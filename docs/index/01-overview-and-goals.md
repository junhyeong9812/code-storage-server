## CTS란

**Code Storage(CTS)** 는 Git과 유사한 일을 하지만, Git의 코드/프로토콜/포맷에 **전혀 의존하지 않고 처음부터** 만든 버전 관리 시스템이다. 학습 목적이 크며, "버전 관리 시스템은 내부에서 어떻게 동작하는가"를 직접 구현하며 이해하는 데 초점이 있다.

세 개의 실행 산출물이 있다:

1. **`cts` CLI** — 로컬에서 저장소를 만들고 커밋하고 서버와 동기화한다.
2. **CTS 서버** — 저장소를 호스팅하고 REST API를 제공하며 CI/CD 빌드를 돌린다.
3. **Web UI** — 브라우저에서 저장소/커밋/파일/빌드를 둘러본다.

## 핵심 아이디어: 내용 주소 지정(content-addressed)

Git과 마찬가지로 CTS의 심장은 **"내용의 해시가 곧 객체의 이름"** 이라는 발상이다.

- 파일 내용 → **Blob**, 그 내용의 SHA-256 해시가 식별자
- 디렉토리 구조 → **Tree**(이름→해시 목록)
- 스냅샷 → **Commit**(루트 Tree + 부모 + 메타데이터)

같은 내용은 같은 해시 → **자동 중복 제거**. 한 글자만 바뀌어도 해시가 완전히 달라짐 → **무결성 검증**. 이 한 가지 원리에서 버전 관리의 거의 모든 성질이 따라 나온다. (자세히는 [04. 핵심 객체 모델](04-core-object-model.md))

## Git과의 의도적 차이

| 항목 | Git | CTS |
|------|-----|-----|
| 해시 | SHA-1 | **SHA-256** (더 안전) |
| 객체 직렬화 | 자체 바이너리 | blob=원본 / tree·commit=**JSON** |
| 전송 프로토콜 | smart/dumb HTTP, pack negotiation | **bulk 번들**(도달가능 객체 한 번에) — 단순화 |
| 서버 저장 | 객체 파일 | **관계형 DB(메타) + 파일시스템(내용)** |
| 언어/런타임 | C | **Rust** (메모리 안전, 타입 안전) |

CTS는 "정확함과 이해 가능함"을 효율보다 우선한다. 예를 들어 push는 매번 커밋에서 도달 가능한 전체 객체를 보내되 서버가 중복을 건너뛴다 — Git의 정교한 협상보다 단순하지만 원리는 같다.

## 목표 (README 기준)

- Git 없이 동작하는 독립 버전 관리 시스템
- 자체 CLI (`cts`)
- 자체 서버 및 저장소 호스팅
- 자체 CI/CD 파이프라인
- 인증/인가 및 협업 권한, 웹 UI

## 완성된 범위 (Phase 1~12)

Core → Server CRUD → CLI 로컬 → Push/Pull → Branch → Build → Web UI → 인증/인가 → 협업 권한 → 토큰 철회 → Web 로그인 → 빌드 자동 트리거.
단계별 상세는 [11. 개발 여정](11-phase-journey.md).

## 의식적으로 남긴 한계 (학습 프로젝트로서)

- push 객체 협상/델타 없음(전체 closure 전송, 서버가 스킵)
- 빌드 러너는 샌드박스 없는 로컬 셸 (포트라 Docker 러너로 교체 가능)
- 토큰 access/refresh 회전 없음(단일 JWT + jti 철회)
- 머지/리베이스/충돌 해결 미구현

이 한계들은 각 `docs/plans/<phase>/task.md`의 "한계/후속" 절에 정리되어 있어, 다음에 무엇을 확장할 수 있는지 알 수 있다.
